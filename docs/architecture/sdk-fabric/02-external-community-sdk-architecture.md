# External Community SDK Architecture

## Objective
A human developer or AI coding harness identifies what it is building; the SDK returns the applicable contracts, surfaces, security rules, templates, examples and tests.

Developer/AI -> classify -> describe-category -> SDK kit -> build -> validate -> install -> grant -> enable -> operate -> revoke.

## Canonical categories
| Category | Example | Purpose |
|---|---|---|
| harness | Pi/coding-agent | AI/harness runtime |
| tool | utility | bounded tools |
| connector | GitHub/MCP/API | external systems |
| communication | email/messaging | communication |
| data-source | memory/knowledge | retrieval/intake |
| ui | viewer/dashboard | presentation |
| service | background/local service | host-mediated service |

## Community SDK 0.1 basis
- Pi: Provider Profiles, primary-agent, dynamic tool rail/workspace, lifecycle.
- Utility Tool: bounded tool + generic surface.
- Reference Memory: basis for replaceable memory provider.
- GitHub: recommended next connector reference.

## Stable public boundary
Manifest/classification; validator/category discovery; capability/grant lifecycle; approved runtime/service contracts; declarative surfaces; Provider Profiles; system-slot eligibility; public errors/examples/tests.

## Near-term
Interface ownership/type; connector reference; AI-harness scaffolding; SDK versioning independent of internal ROS revisions.
