# ResonantOS Browser UX Audit - 2026-06-01

## Purpose

Evaluate the current browser-first ResonantOS experience against the product rule:

- clarity before density
- minimum text required to act
- important settings first
- advanced controls available but progressively disclosed
- one coherent human model: full AI workspace when starting from ResonantOS, side-panel AI when browsing

## Current Strengths

- The app now has a real Chromium-family browser host with Phantom available and pinned.
- The ResonantOS extension and Phantom are pinned, which makes the browser-first architecture visible.
- The main workspace, side-panel chat, browser jobs, settings, Hermes, OpenCode, and Living Archive surfaces are modular rather than one page blob.
- Settings now has a clearer sub-sidebar and can deep-link to specific sections such as Profile, Providers, and Memory.
- The chat composer has converged toward one control model across main workspace and side panel.
- Browser control has visible agent-state feedback, stop controls, and deterministic job tracking.

## UX Problems To Fix

### P0 - ResonantOS should own the first impression

Observed rendered state: the installed app can open to a standard Chromium/Google new tab with Chromium banners, while ResonantOS is only available through the pinned extension.

Why this is a problem:

- It makes the product feel like a modified browser rather than ResonantOS.
- New users will not know whether they should type into Google, click the ResonantOS extension, or use the side panel.
- It conflicts with the intended Comet-like model: new tab equals AI workspace; browsing equals page plus AI side panel.

Required outcome:

- New window/new tab should open the ResonantOS main workspace by default.
- The side panel should be closed in main workspace mode and open when the user enters a normal webpage/browsing context.
- Chromium restore/API/default-browser warning surfaces should be suppressed or replaced where technically safe.

### P1 - Settings must stay layered

Current direction is correct, but settings should be stricter about hierarchy.

Required outcome:

- Profile, Providers, Memory, Browser Control, Add-ons, and Privacy should remain top-level user-facing settings.
- Advanced diagnostics, route internals, raw provider metadata, and logs should be behind Advanced/Diagnostics.
- Each settings section should start with the one action the user is most likely trying to perform.

### P1 - Memory needs a human-first explanation, not implementation-first language

The Living Archive is powerful but easy to misunderstand.

Required outcome:

- The first visible explanation should say: "Human Knowledge is preserved; AI Memory is the maintained wiki."
- Technical terms like promotion, review artifact, intake bundle, and source version should be secondary.
- Obsidian should be presented as an optional way to manage the same memory files, not as a requirement.

### P1 - Browser control must separate "what the AI is doing" from "what the page is"

The moving control overlay is directionally right.

Required outcome:

- Page overlay stays active for the full agent-control run, not per step.
- Bottom activity pill shows the current action in human language: reading, clicking, typing, verifying, waiting for user.
- Chat timeline should show completed steps, but should not expose internal planner noise unless expanded.

### P2 - Sidebar density should remain compact

Recent sidebar work improved legibility, but the rule should be explicit.

Required outcome:

- Row actions appear on hover.
- Names are not truncated just because actions exist.
- Projects are real user folders/workspaces, not add-on shortcuts.
- Add-ons live under pinned add-ons or add-ons, not under projects.

## Product Standard Going Forward

For every new screen:

1. The first visible block must answer: "What is this and what do I do next?"
2. The primary action must be visible without scrolling.
3. Secondary details must be collapsible or lower on the page.
4. Technical state is allowed only when it changes a user decision.
5. Advanced controls must not compete visually with the main action.
6. Touch targets should be large enough for touch-first use, while text density remains desktop-efficient.
7. Tests must include at least one rendered or installed-app check for major UI changes.

## Recommended Next Implementation Step

Fix the first-run/new-tab experience:

- make ResonantOS main workspace the default new-tab/new-window destination
- keep the AI side panel closed on the main workspace
- auto-open the side panel only on normal web pages
- suppress or route around Chromium startup warnings where safe
- add deterministic verification that the installed app opens directly into the ResonantOS main workspace

This is the highest-leverage UX fix because it clarifies what the product is before the user reads any text.

## 2026-06-01 Implementation Note

The first-run/new-tab contract is now implemented in code:

- the ResonantOS extension declares `chrome_url_overrides.newtab`
- the launcher seeds startup preferences to open the ResonantOS main workspace
- stale crash-restore state is reset before launch
- native Chromium startup adds first-run/default-browser/crash-restore suppression flags
- the native CEF host redirects restored or newly-created `chrome://newtab` pages back to the ResonantOS workspace when browser-first mode is active
- contract tests verify the new-tab ownership and native startup flags

Verification note:

- the installed-app verifier proves the app loads `src/main-workspace.html`
- a fresh remote-debugging launch proves the main workspace is present and no raw `chrome://newtab` page remains active
- macOS CrashReporter dialogs from forced test shutdowns can still obscure screenshots; use graceful quit paths for visual proof
