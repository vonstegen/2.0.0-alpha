Welcome — what ResonantOS is, in plain English

ResonantOS is a workspace for AI tools. Think of it like a wall of electrical outlets: the wall is always there, and any device that matches the outlet shape can plug in and get power.

That outlet shape is what we call the SDK — the Software Development Kit. The SDK is the rulebook that says "to plug into ResonantOS, your tool must speak this language, declare what it needs, and respect what it isn't allowed to do."

This guide is itself a tool that plugged in using the SDK. Right now, you are using a third workspace add-on (alongside Resonant Echo and Resonant Counter) that did not require any change to ResonantOS Core. It just declared its manifest, and the host picked it up.

Replaceability is the whole point: any third party should be able to ship an add-on without asking the host for permission or code review.
Step 2 of 7

How an add-on gets in

An add-on goes through six stages before it can serve you:

  1. Manifest. The add-on ships a small JSON file declaring its name, version, capabilities, and the routes it offers.
  2. Discovery. ResonantOS scans the add-ons directory on startup and lists everything it finds.
  3. Validation. The host reads the manifest, checks the capability grant against the policy, and rejects anything mis-declared.
  4. Activation. The bridge launches the add-on's runtime as a subprocess, on its declared port.
  5. Capability grant. The bridge hands the add-on a token bound only to the capabilities it was granted.
  6. Round-trip. The iframe inside the workspace uses the bridge token to call the add-on. The bridge re-checks every request and the add-on re-checks it again at its boundary.

This guide is currently in step 6 — it's calling its own routes through the bridge right now.

Defense in depth: the host AND the add-on BOTH check the capability token on every request. Neither has to trust the other.

What this add-on can and can't do

Look at the manifest of the add-on you are using right now. It declares capabilities under three buckets:

BucketCapabilityWhat it means
Grantedharness-messagingSend and receive messages through the bridge.
Deniedwallet-signingSign transactions or authorize payments.
Deniedprovider-secret-readRead provider API keys or secrets.
Deniedtrusted-memory-writeModify ResonantOS trusted memory (your long-term notes).
Deniedfilesystem-writeWrite to the host filesystem.

The host has a fixed policy that says: "even if this add-on requests these denied capabilities, I will not issue a token." The bridge returns 400 Unknown bridge capability requested if you try.

The grant is decided by the host's policy, not by the add-on. The add-on can ask; only the host can say yes.

Step 6 of 7

What's been built (and proved)

  • Generic add-on registry. Host reads manifests, lists add-ons, drives the UI. No code knows any specific add-on ID.
  • Workspace resolver. The "Open" button uses a generic proxyPath field. Echo, Counter, and now SDK Guide all opened through the SAME code path.
  • Bridge reverse-proxy. All /echo/*, /counter/*, and /sdk-guide/* paths route through a single dispatcher with longest-prefix match.
  • Capability tokens. Bootstrap token mints per-capability tokens. Bridge re-checks every request; addon upstream re-checks again.
  • Isolated iframe renderer. Each add-on runs in a sandboxed srcdoc iframe with explicit CSP. The bridge token is the only cross-boundary credential.
  • Syntax gate. All extension modules pass a syntax check before commit.
  • Resonant Echo and Resonant Counter. Two reference add-ons onboarded via the SAME generic mechanism, proving replaceability end-to-end.

Next steps for a developer (and for ResonantOS)

Build your own add-on. Drop a folder under browser-first/addons/<your-name>/ with addon.json, index.html, and server.mjs. Copy the structure of Resonant Echo or this guide. Declare your capabilities honestly. The host will pick you up.

What comes after Grok M1. A marketplace where anyone can ship a workspace add-on without code review; ResonantOS Core remains a thin, audited host.
